# LangGraph + PostgreSQL SQL Agent

A small teaching/demo project showing a **real LangGraph agent loop** with:

- LangGraph `StateGraph`
- Ollama + Qwen
- PostgreSQL
- Adminer database UI
- A custom `execute_sql` tool
- `ToolNode`
- Conditional routing
- A visible message/tool trace

## Architecture

```text
                         tool call
                    +----------------+
                    |                v
START ---> agent ---> router ---> tools
            ^                    |
            |____________________|
              ToolMessage

If the agent does not request a tool:

agent ---> router ---> END
```

The **LLM decides whether to request the SQL tool**.
LangGraph handles orchestration/routing.
`ToolNode` executes the requested Python tool.
The Python tool talks to PostgreSQL.

## How the code works

### State

```python
class State(TypedDict):
    messages: Annotated[list, add_messages]
```

The LangGraph state contains the conversation messages. `add_messages` tells
LangGraph to append new messages to the existing state.

A typical run becomes:

```text
HumanMessage
AIMessage(tool call)
ToolMessage(SQL result)
AIMessage(final answer)
```

### SQL tool

```python
@tool
def execute_sql(query: str) -> str:
```

This is ordinary Python wrapped as a LangChain/LangGraph-compatible tool.

The docstring matters: it becomes part of the tool description the LLM sees.

### Tool binding

```python
llm_with_tools = llm.bind_tools(tools)
```

This does not execute a tool.

It tells the model which tools are available and gives it their schemas and
descriptions. The model can then produce a structured tool-call request.

### Agent node

```python
def agent_node(state: State):
```

This invokes Qwen. Qwen can either:

1. produce a final natural-language answer, or
2. request `execute_sql`.

### Router

```python
def should_continue(state: State):
```

The router does not decide which SQL query should be executed.

It only checks whether the last AI message contains a tool call.

Tool call present:

```text
agent -> tools
```

No tool call:

```text
agent -> END
```

### ToolNode

```python
tool_node = ToolNode(tools)
```

`ToolNode` receives the tool call generated by Qwen and invokes the matching
Python tool.

### Loop

```python
builder.add_edge("tools", "agent")
```

This is what creates the agent loop.

After PostgreSQL returns data, `ToolNode` creates a `ToolMessage`. That message
goes back to Qwen. Qwen sees the database result and can formulate the final
answer (or request another tool call).

## Example flow

Question:

```text
Who has the highest salary?
```

Conceptually:

```text
HumanMessage
     |
     v
   agent / Qwen
     |
     | tool call:
     | execute_sql(
     |   SELECT name, salary
     |   FROM employees
     |   ORDER BY salary DESC
     |   LIMIT 1
     | )
     v
 ToolNode
     |
     v
PostgreSQL
     |
     | Kiran, 120000
     v
 ToolMessage
     |
     v
 agent / Qwen
     |
     v
"Kiran has the highest salary at 120,000."
     |
     v
    END
```

## Reset the sample database

The initialization SQL runs automatically only when PostgreSQL creates a new
data directory.

To completely reset the demo:

```bash
docker compose down -v
docker compose up -d
```

Warning: `-v` deletes the PostgreSQL Docker volume for this demo.

## Stop the containers

```bash
docker compose down
```

## Production note

This is intentionally a small educational agent.

For production, do not rely only on checking that generated text starts with
`SELECT`. Use a dedicated PostgreSQL account with SELECT-only permissions,
schema/table allowlists, query timeouts, row limits, auditing, and stronger SQL
validation.
